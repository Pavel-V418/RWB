# ADR-004. Backend-агент: вызов LLM на тег, шлюзы сборки, политики и тестов, ремонт по обратной связи

## Контекст и постановка проблемы
Доменную логику (геозапросы, сессии, таймеры, события) пишет LLM qwen3.8-27b: 32k входного контекста, 30 000 токенов
в минуту на ключ. Код должен собираться, проходить тесты и не содержать опасных конструкций, а ошибки времени
выполнения — исправляться без ручного переписывания.

## Статус
ПРИНЯТО

## Альтернативы

### Вариант 1. Один запрос на всё приложение
- Плюсы
  - модель видит всю картину.
- Минусы
  - контекст не помещается в 32k; одна ошибка ломает весь результат; ремонт дорогой.

### Вариант 2. Запрос на тег OpenAPI (`I<Tag>Api`) с узким контекстом и шлюзами
- Плюсы
  - контекст 6–8 тыс. токенов: операции тега, DTO, сущности, ограничения БД, интеграции;
  - сбой одного тега не мешает остальным; после исчерпания попыток — детерминированная заглушка 501, сборка зелёная;
  - ремонт точечный: ошибки компилятора, политики или e2e возвращаются модели.
- Минусы
  - модель не видит соседние теги — соглашения (типы событий, виды уведомлений) приходится извлекать и подавать отдельно.

## Принятое решение
Вариант 2. Шлюзы по порядку: политика безопасности (SEC001 — сырой SQL, SEC002 — `DateTime.Now`) → `dotnet build -warnaserror`
→ интеграционные тесты по критериям приёмки (xUnit + Testcontainers, `dotnet test` по классу тега). Режим `--feedback`
ремонтирует тег по тексту ошибки работающего стенда (e2e, логи), начиная с текущего кода; неудачный ремонт код не портит.
Псевдотег `Jobs` — фоновые задачи (таймеры) на `TimeProvider`.

## Последствия принятого решения
- Каждая попытка и ответ модели сохраняются в `04_backend/.agent/`, итог — `backend-agent.json` (токены, попытки, статус тегов и тестов).
- Тест, который не прошёл за все попытки, не удаляется и не подгоняется: он помечается Skip с причиной и уходит на ремонт кода.
- Проверено на кейсе 1: все теги реализованы агентом, e2e стенда 26 из 26 шагов.
