# ADR-003. События доставляются через transactional outbox → Kafka → SignalR

## Контекст и постановка проблемы
Требования кейсов включают модель событий (въезд, выход, смена зоны, жизненный цикл сессии и т. п.), журнал событий
в админке и уведомления в реальном времени. Если публиковать в Kafka прямо из обработчика запроса, при сбое между
записью в БД и отправкой событие теряется или уходит событие о несохранённых данных.

## Статус
ПРИНЯТО

## Альтернативы

### Вариант 1. Публикация в Kafka из обработчика запроса
- Плюсы
  - просто, без дополнительной таблицы;
  - минимальная задержка.
- Минусы
  - нет атомарности с транзакцией БД: потеря или «фантомные» события;
  - недоступность Kafka ломает API.

### Вариант 2. Transactional outbox: событие пишется в таблицу в той же транзакции, фоновый диспетчер публикует
- Плюсы
  - событие сохраняется тогда и только тогда, когда сохранены данные;
  - Kafka недоступна — API работает, события копятся (здоровье Degraded, а не Unhealthy);
  - повторы и DLQ после исчерпания попыток.
- Минусы
  - задержка доставки на интервал диспетчера;
  - доставка «как минимум один раз» — потребители должны быть идемпотентны.

## Принятое решение
Вариант 2. Агент вызывает `outbox.Enqueue(...)` до `SaveChangesAsync`; диспетчер каркаса публикует в топики Kafka
(ключ партиции — идентификатор агрегата, например vehicleId), неудачные — в DLQ; события ретранслируются в хаб SignalR `/hubs/events`.
Журнал для админки — отдельная доменная таблица (`domain_events`) в той же транзакции.

## Последствия принятого решения
- Метрики `app_outbox_published`, `app_outbox_publish_failures`, `app_outbox_dead_lettered`; health-проверка `outbox` переходит
  в Degraded, если события ждут дольше порога.
- Конверт события (envelope) единый для Android, web и Kafka.
