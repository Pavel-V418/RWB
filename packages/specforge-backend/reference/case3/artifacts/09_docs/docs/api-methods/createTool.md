## 1. Назначение

Добавить инструмент в каталог.

Транспорт: HTTPS (TLS 1.2+), HTTP/1.1. Схема взаимодействия: синхронный запрос — ответ. Формат тела: JSON, UTF-8.

## 2. Входные данные (Входящие параметры)

### Авторизация

JWT в заголовке `Authorization: Bearer <token>`; роль пользователя берётся из claims токена.

### Заголовки

| Наименование | Описание | Тип данных | Обязательность | Пример |
| --- | --- | --- | --- | --- |
| Authorization | токен доступа | string | да | `Bearer eyJhbGciOi…` |
| Content-Type | формат тела запроса | string | да | `application/json` |
| X-Correlation-Id | сквозной идентификатор запроса; если не передан — генерируется сервером | string | нет | `req-20261030-0001` |

### Параметры path

Отсутствуют.

### Параметры query

Отсутствуют.

### Модель данных тела запроса

| Поле | Описание | Тип данных | Обязательность | Варианты значений | Поле БД |
| --- | --- | --- | --- | --- | --- |
| inventoryNumber | — | string | да | до 50 симв.; regex `^[A-Z0-9-]{3,50}$` | `tools.inventory_number` |
| name | — | string | да | до 200 симв. | `tools.name` |
| category | — | string | да | до 100 симв. | `tools.category` |
| warehouse | — | string | да | до 100 симв. | `tools.warehouse` |
| status | — | string (enum) | да | `available`, `issued`, `reserved`, `repair`, `lost`, `retired`; по умолчанию `available` | `tools.status` |

Если обязательное поле не передано или не проходит проверку — ответ 400 с перечнем полей в `errors`. Лишние поля отклоняются (`additionalProperties: false`).

### Пример запроса

```http
POST /api/v1/tools HTTP/1.1
Host: localhost:8080
Authorization: Bearer <token>
Content-Type: application/json

{
  "inventoryNumber": "INV-000123",
  "name": "строка",
  "category": "строка",
  "warehouse": "строка",
  "status": "available"
}
```

### Кому разрешено вызывать метод

- Руководитель склада (`warehouse_manager`)

Остальным ролям — ответ 403.

### Неуспешная обработка запроса

| HTTP Code | Описание |
| --- | --- |
| 400 | Ошибка валидации запроса |
| 401 | Нет или истёк токен доступа |
| 403 | Недостаточно прав для операции |
| 409 | Конфликт состояния ресурса: Инвентарный номер уже существует |
| 422 | Нарушено бизнес-правило: Некорректные входные данные |
| 500 | Внутренняя ошибка |

#### Модель данных тела ответа (application/problem+json, RFC 9457)

| Поле | Описание | Тип данных | Обязательность |
| --- | --- | --- | --- |

| status | HTTP-код | integer | да |
| detail | подробности | string | нет |
| code | машиночитаемый код бизнес-ошибки | string | нет |

## 4. Описание алгоритма работы метода

**Основной сценарий:**

1. Проверить права роли warehouse_manager
2. Валидировать входные данные: инвентарный номер, наименование, категория, склад, состояние
3. Проверить уникальность инвентарного номера
4. Сгенерировать QR-код на основе инвентарного номера
5. Сохранить запись Tool в базу данных
6. Зафиксировать событие created в MovementHistory
7. Зафиксировать действие в AuditLog
8. Вернуть созданную запись Tool с QR-кодом

**Сценарий исключений:**

- Инвентарный номер уже существует → 409
- Некорректные входные данные → 422

**Проверки и валидации:**

- `inventoryNumber`: до 50 симв.; regex `^[A-Z0-9-]{3,50}$`, обязательно
- `name`: до 200 симв., обязательно
- `category`: до 100 симв., обязательно
- `warehouse`: до 100 симв., обязательно
- `status`: `available`, `issued`, `reserved`, `repair`, `lost`, `retired`; по умолчанию `available`, обязательно

**Кэширование:** не применяется.

**Производительность:** таймаут обработки 30 с.
