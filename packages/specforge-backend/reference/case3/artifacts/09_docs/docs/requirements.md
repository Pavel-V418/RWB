# Модель требований: Система учёта выдачи и возврата инструмента

> Сгенерировано автоматически из `requirements.json`. Не редактируйте вручную: правки вносятся во вход или в `answers.yaml`, затем этап перезапускается.

Система для учёта выдачи и возврата дорогостоящего инструмента и оборудования со склада технических служб. Она позволяет вести каталог, бронировать, выдавать и возвращать инструмент с фиксацией состояния, а также передавать события в корпоративную систему учёта ТМЦ.

## Профиль решения

Включено: web-интерфейс, админка, мобильное приложение, асинхронные события, фоновые задачи и таймеры, файлы.
Не требуется: геоданные, обновления в реальном времени, уведомления пользователю.

- Мобильное приложение прямо требуется для кладовщика
- Web-интерфейс для руководителя склада
- Kafka для передачи событий во внешнюю систему
- Загрузка справочника из файла
- Контроль срока возврата требует scheduled jobs

## Сущности

- **ENT-Tool** — Единица инструмента или оборудования Атрибуты: `inventoryNumber`: string, `name`: string, `category`: string, `warehouse`: string, `status`: enum, `qrCode`: string.
- **ENT-Employee** — Сотрудник, получающий инструмент Атрибуты: `id`: uuid, `name`: string, `passNumber`: string.
- **ENT-Reservation** — Бронирование инструмента на дату Атрибуты: `id`: uuid, `toolId`: uuid, `employeeId`: uuid, `date`: date.
- **ENT-IssueRecord** — Запись о выдаче инструмента Атрибуты: `id`: uuid, `toolId`: uuid, `employeeId`: uuid, `issueDate`: datetime, `returnDeadline`: datetime.
- **ENT-ReturnRecord** — Запись о возврате инструмента Атрибуты: `id`: uuid, `toolId`: uuid, `employeeId`: uuid, `returnDate`: datetime, `condition`: enum.
- **ENT-MovementHistory** — История движения инструмента Атрибуты: `id`: uuid, `toolId`: uuid, `eventType`: enum, `timestamp`: datetime.
- **ENT-SyncQueue** — Очередь синхронизации операций Атрибуты: `id`: uuid, `operationType`: enum, `payload`: json, `status`: enum.

## Пользовательские сценарии

### UC_001. Добавление инструмента и печать QR-кода

Актор: Руководитель склада. Цель: Добавить новую единицу инструмента в каталог и получить QR-код для печати. Требования: FR-1, FR-2, FR-12.

Предусловия:

- warehouse_manager аутентифицирован в web-интерфейсе
- Склад выбран в системе

Основной поток:

1. warehouse_manager открывает форму добавления инструмента
2. warehouse_manager вводит инвентарный номер, наименование, категорию, склад и состояние
3. Система проверяет уникальность инвентарного номера
4. Система сохраняет запись Tool и генерирует QR-код
5. Система отображает QR-код для печати

Альтернативные потоки:

- Шаг 3: инвентарный номер уже существует → Система показывает ошибку «Инвентарный номер уже существует» и не сохраняет запись

Исключения:

- Шаг 2: не заполнены обязательные поля → Система блокирует сохранение и подсвечивает пустые поля
- Шаг 4: сбой сохранения в PostgreSQL → Система показывает сообщение об ошибке и не создает QR-код

Постусловия:

- Запись Tool сохранена в базе данных
- QR-код сгенерирован и доступен для печати

Ожидаемый результат: warehouse_manager видит сохраненный инструмент в каталоге и QR-код для печати

### UC_002. Бронирование инструмента сотрудником

Актор: Сотрудник. Цель: Забронировать инструмент на конкретную дату. Требования: FR-4, FR-13.

Предусловия:

- employee аутентифицирован в системе
- Инструмент доступен в каталоге

Основной поток:

1. employee выбирает инструмент из каталога
2. employee указывает дату бронирования
3. Система проверяет доступность инструмента на указанную дату
4. Система создает запись Reservation
5. Система подтверждает бронирование

Альтернативные потоки:

- Шаг 3: инструмент уже забронирован на эту дату → Система показывает сообщение «Инструмент уже забронирован»

Исключения:

- Шаг 2: дата в прошлом → Система показывает ошибку «Дата не может быть в прошлом»
- Шаг 4: сбой сохранения → Система показывает сообщение об ошибке

Постусловия:

- Запись Reservation сохранена в базе данных

Ожидаемый результат: employee видит подтверждение бронирования

### UC_003. Выдача инструмента сотруднику

Актор: Кладовщик. Цель: Выдать инструмент сотруднику, отсканировав QR-код инструмента и пропуск сотрудника. Требования: FR-3, FR-5, FR-14, FR-10.

Предусловия:

- warehouse_keeper аутентифицирован в мобильном приложении
- Инструмент находится на складе
- Сотрудник присутствует

Основной поток:

1. warehouse_keeper сканирует QR-код инструмента
2. Система идентифицирует инструмент по QR-коду
3. warehouse_keeper сканирует пропуск сотрудника
4. Система идентифицирует сотрудника по номеру пропуска
5. Система проверяет, не забронирован ли инструмент другим сотрудником
6. Система создает запись IssueRecord
7. Система фиксирует событие выдачи в MovementHistory

Альтернативные потоки:

- Шаг 5: инструмент забронирован другим сотрудником → Система показывает отказ в выдаче

Исключения:

- Шаг 2: QR-код не найден → Система показывает «Инструмент не найден»
- Шаг 4: пропуск не найден → Система показывает «Сотрудник не найден»
- Шаг 6: потеря связи с сервером → Система сохраняет операцию локально в SyncQueue

Постусловия:

- Запись IssueRecord сохранена
- Событие выдачи зафиксировано в MovementHistory
- Инструмент помечен как выданный

Ожидаемый результат: warehouse_keeper видит подтверждение выдачи

### UC_004. Возврат инструмента с оценкой состояния

Актор: Кладовщик. Цель: Зафиксировать возврат инструмента с оценкой состояния. Требования: FR-6, FR-17.

Предусловия:

- warehouse_keeper аутентифицирован в мобильном приложении
- Инструмент выдан сотруднику

Основной поток:

1. warehouse_keeper сканирует QR-код возвращаемого инструмента
2. Система находит активную запись IssueRecord
3. warehouse_keeper выбирает состояние: исправен, требует ремонта, утерян
4. Система создает запись ReturnRecord
5. Система фиксирует событие возврата в MovementHistory
6. Система обновляет состояние инструмента

Альтернативные потоки:

- Шаг 3: состояние «требует ремонта» → Система помечает инструмент как требующий ремонта

Исключения:

- Шаг 2: нет активной выдачи → Система показывает «Нет активной выдачи для этого инструмента»
