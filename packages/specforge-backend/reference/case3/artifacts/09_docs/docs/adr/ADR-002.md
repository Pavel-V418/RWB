# ADR-002. Механизм передачи событий во внешнюю систему

ADR (Architecture Decision Record) фиксирует выбор между альтернативами, обоснование и последствия.

## Контекст и постановка проблемы

Система должна передавать данные о выдаче, возврате и списании инструмента в корпоративную систему учёта ТМЦ. Прямое синхронное вызовы API внешней системы создаёт риск блокировки основной бизнес-логики при недоступности внешней системы.

## Статус

ПРЕДЛОЖЕНО | **ПРИНЯТО** | ЗАМЕНЕНО

## Альтернативы

### Вариант 1. Асинхронная шина событий Kafka

Плюсы:

- Отказоустойчивость: события сохраняются в очереди при недоступности потребителя
- Развязка систем: внешняя система не влияет на производительность основной системы
- Возможность масштабирования потребителей

Минусы:

- Необходимость развертывания и обслуживания кластера Kafka
- Усложнение архитектуры за счёт дополнительного компонента

### Вариант 2. Прямые HTTP-вызовы API внешней системы

Плюсы:

- Простота реализации и отсутствие дополнительных инфраструктурных компонентов
- Легкость отладки

Минусы:

- Риск потери данных при сбое внешней системы
- Зависимость времени отклика основной системы от доступности внешней
- Необходимость реализации сложных механизмов повторных попыток и очередей на уровне приложения

## Принятое решение

Использовать Kafka для передачи событий. События содержат минимальный набор данных (eventType, toolId, employeeId, timestamp, payload). Это обеспечивает асинхронность и отказоустойчивость интеграции, как указано в архитектурных заметках.

## Последствия принятого решения

- Добавлен компонент Kafka Broker в инфраструктуру
- Реализован mock-потребитель для тестирования интеграции
- События могут задерживаться при проблемах с Kafka, но не теряются

## Ответственные

- Архитектор
- Инженер по интеграциям
