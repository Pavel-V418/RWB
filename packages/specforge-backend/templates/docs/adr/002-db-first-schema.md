# ADR-002. Схема БД — источник истины (DB-first), EF-модель выводится из DDL

## Контекст и постановка проблемы
Архитектор (участник 2) выпускает DDL PostgreSQL/PostGIS вместе с OpenAPI. Нужна модель EF Core для доменной логики.
Если модель и схема живут отдельно (code-first + миграции), они расходятся: CHECK, enum, геометрии и значения по умолчанию
теряются или дублируются.

## Статус
ПРИНЯТО

## Альтернативы

### Вариант 1. Code-first: сущности C# и миграции EF
- Плюсы
  - привычно для .NET-разработчиков;
  - миграции версионируются вместе с кодом.
- Минусы
  - DDL архитектора пришлось бы переписывать в C#, ограничения CHECK и функции PostGIS теряются;
  - два источника правды о схеме.

### Вариант 2. DB-first: DDL применяется как есть, сущности генерируются scaffold-ом
- Плюсы
  - схема в БД ровно та, что спроектировал архитектор, со всеми CHECK, индексами GiST и SQL-функциями;
  - модель EF всегда совпадает со схемой (проверяет интеграционный тест `PersistenceModelTests`).
- Минусы
  - нужны свои шаблоны T4 и постобработка (enum PostgreSQL → varchar + CHECK, литеральные DEFAULT);
  - эволюция схемы — новые SQL-файлы, а не миграции EF.

## Принятое решение
Вариант 2. `generators/gen-ef.sh`: DDL нормализуется, применяется во временном PostGIS, `dotnet ef dbcontext scaffold`
со своими шаблонами. Платформенные таблицы каркаса (outbox, idempotency) — в `db/000_platform.sql`, доменные — `db/100_domain.sql`.
На стенде SQL применяется init-скриптами PostgreSQL при пустом томе.

## Последствия принятого решения
- Ограничения БД попадают в контекст backend-агента (CHECK, длины varchar, SQL-функции) и в генерацию тестов.
- Шлюз падает, если scaffold молча пропустил колонку или таблицу.
- Изменение схемы требует пересоздания тома стенда (или ручного SQL-патча) — для хакатонного стенда допустимо.

## Ответственные
Участник 3 (backend + DevOps), участник 2 (архитектор, DDL).
