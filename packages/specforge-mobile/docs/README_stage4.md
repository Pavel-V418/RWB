# Этап 4 — Android-агент (участник 5)

Агент получает UX-спеку, требования и клиент API и пишет слой экранов `feature/` поверх каркаса `android/`.
Затем прогоняет шлюз (сборка, тесты, снимки экранов) и исправляет ошибки, максимум 3 попытки ремонта.

```
agents/android_agent/
  agent.py      run(input_dir, output_dir, llm) → GateResult — главный цикл
  context.py    сжатие входов: UX-спека, выжимка требований, сигнатуры API и ядра
  prompts.py    промпты: план → данные → экран → сборка → ремонт
  workspace.py  копия каркаса, запись файлов только по контракту, откат замороженных файлов
  llm.py        клиент OpenAI-совместимого /chat/completions (Qwen организаторов)
  replay.py     «LLM» без сети: отвечает эталоном кейса №1 (проверка механики)
  run.py        запуск из командной строки
  test_android_agent.py  8 тестов механики (без LLM и Gradle, ~2 с)
```

## Как работает
1. `prepare`: каркас копируется в `<out>/project`, папка `feature/` очищается. Эталон в `android/` не трогается.
2. **План** (1 вызов LLM, JSON): экраны, репозитории, навигация. UX-спека главнее плана: недостающие экраны
   и состояния агент добавляет сам.
3. **Данные** (1 вызов): модели, репозитории, `GeneratedApi`, `FeatureModule`, фейки для тестов.
4. **Экраны** (по 1 вызову на экран): ViewModel, Route/Screen, `strings_<screenId>.xml`, тест ViewModel.
5. **Сборка** (1 вызов): `AppRoot` (навигация) и `ScreenshotTest` (все состояния из спеки).
6. **Шлюз** `tools/android_gate`, затем проверка, что есть снимок каждого состояния каждого экрана.
7. **Ремонт**: в LLM уходят только ошибки и упавшие файлы, остальное — сигнатурами. Запись вне `feature/`
   отклоняется, изменённые замороженные файлы откатываются без LLM.

Результат в `<out>/`: `gate_report.json` (GateResult для участника 1), `plan.json`, `agent_log.json`
(токены и время по шагам), `screenshots/` (для VLM-ревьюера участника 4), `project/` (готовый проект).

## Запуск (из корня `project rwb`, в PowerShell)
Проверка механики без LLM (около 1 мин, нужен JDK 21):
```
py -m agents.android_agent.run --in reference/case1 --out build/agent_smoke --replay
```
Настоящий запуск с LLM. Переменные задаются только в текущем окне, в файлы их не записывать:
```
$env:LLM_BASE_URL="<адрес из сообщения организаторов, заканчивается на /v1>"
$env:LLM_MODEL="<имя модели>"
$env:LLM_API_KEY="<ключ>"
py -m agents.android_agent.run --in reference/case1 --out build/agent_case1
```
В пайплайне: `--in artifacts --out artifacts/06_android`. Для другого кейса: `--api-client <папка клиента>`.
Тесты механики: `py -m unittest agents.android_agent.test_android_agent -v`.

## Проверено
- 10 тестов механики: разбор ответов (в том числе без блоков FILE), контракт путей, откат ядра, цикл ремонта,
  лимит попыток, поиск связанных файлов, сверка со спекой.
- Дымовой прогон с настоящим Gradle на реплее: ПРОЙДЕН с 1-й попытки, 21 тест, 6 снимков, 58 с.

  57,6 тыс. токенов, 4,6 мин.** Результат: `build/agent_case1_full/`.

## Доступ к LLM с ноутбука
Сервер `10.10.10.10:4000` доступен только изнутри vm5, поэтому нужен SSH-туннель в отдельной вкладке терминала
(пароль вводится вручную, вкладку не закрывать):
```
ssh -p 10005 -N -L 4000:10.10.10.10:4000 team5@85.143.113.230
```
После этого `$env:LLM_BASE_URL="http://127.0.0.1:4000/v1"`, `$env:LLM_MODEL="qwen3.8-27b"`.
`--resume` — только шлюз и ремонт уже сгенерированного проекта, без повторной генерации.
Сырые ответы модели сохраняются в `<out>/llm/`.

## Что узнали на реальной модели (исправлено в агенте)
- Qwen на ремонте отвечает блоком ```kotlin без `<<<FILE>>>`: путь выводится из `package` и объявления.
- Модель повторяет одну ошибку, если не видит причину: в ремонт теперь идут файлы, где объявлены идентификаторы
  из ошибки, и пометка «уже пробовал, измени подход».
- Иногда некорректен сам тест (фейк отвечает мгновенно): ремонт разрешает чинить тест, но не ослаблять проверку.
- Сервер общий и отвечает 429: повторы с паузой 5…60 с и с учётом `Retry-After`.

## Скриншот-тесты без LLM (по ответу участника 1)
Агент пишет только экраны и `<Pascal>ScreenSample(state: String)`. Скриншот-тесты генерирует
`tools/android_gate/screens.py` из UX-спеки, по одному на каждую пару «экран × состояние».
Команды для шлюза платформы:
```
python3 tools/android_gate/screens.py . --spec <ux-спека> generate   # перед сборкой
python3 tools/android_gate/screens.py . --spec <ux-спека> check      # нет Sample/состояния → ошибка до Gradle
./gradlew --no-daemon assembleDebug testDebugUnitTest recordRoborazziDebug
python3 tools/android_gate/screens.py . --spec <ux-спека> verify     # все PNG на месте
```
Ошибки печатаются как `file:line:column: error: …` и указывают на Kotlin-файл экрана, а не на спеку.
Поэтому ремонт чинит основной код: папка тестов в ремонте защищена. Эталон кейса №1 переведён на это
соглашение (`LoginSamples.kt`, `SessionSamples.kt`), сборка проходит, снимков 7.
