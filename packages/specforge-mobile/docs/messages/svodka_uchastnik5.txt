===== РЕАЛИЗОВАНО И ПРОВЕРЕНО =====

1. Mock-маршрут и эталон событий (tools/route_player, reference/case1/mock_route)
   - Маршрут по Невскому через реальные демо-зоны 514725 и 514660 из сида участника 3.
   - Генератор эталона универсальный: доменные правила лежат в scenario.json. Правила backend учтены: гистерезис по 2 точкам; выезд → ZoneExited и закрытие сессии; въезд в другую зону в течение 300 с → ZoneChanged.
   - Плеер маршрута с ускорением TIME_SCALE.

2. Каркас Android (android/)
   - Kotlin + Compose, ядро core/ заморожено (frozen.sha256), экраны кейса №1 — эталон.
   - Собирается на JDK 17+, 21 тест зелёный, 7 снимков экранов.
   - Скриншот-тесты генерируются из UX-спеки без LLM (tools/android_gate/screens.py), ошибки выводятся в формате file:line.

3. Android-агент (agents/android_agent)
   - Из UX-спеки, требований и клиента API генерирует экраны, прогоняет шлюз и чинит ошибки (до 3 попыток).
   - На Qwen3.8-27B кейс №1 с нуля проходит со 2-й попытки: 26 тестов, 7 снимков, ~62 тыс. токенов, ~6 мин.

4. Docker-образ песочницы specforge/android:jdk21-api36 (infra/images/android)
   - Собран на vm5. Проверен в условиях песочницы: без сети, 3 ГБ памяти, 512 процессов, не root. Шлюз проходит за 83 с. Размер образа 1,88 ГБ.

5. Контрактные тесты API (tools/contract, ci/tests.gitlab-ci.yml)
   - Проверки строятся из openapi без LLM: 401 без токена и с поддельным, 403 по x-roles, чужой id, Idempotency-Key, 429, отсутствие 5xx.
   - На стенде: 60 проверок, 57 прошли. Находки переданы участнику 3.

6. Security-контур (tools/security, ci/security.gitlab-ci.yml)
   - Semgrep (с правилами под наши SEC), gitleaks, Trivy (fs + образы), ZAP (в CI).
   - Находки приводятся к единому формату и привязываются к SEC-требованиям по категории. LLM-триаж (секреты в модель не уходят, вердикты кэшируются), повторный скан помечает исправленное.
   - Отчёт report.md с итоговым статусом и таблицей «По требованиям безопасности», плюс security.json в формате участника 2.
   - Реальный скан нашего кода: PASSED, 8 находок, 6 ложных (проверено вручную).
   - Провал контрактного теста или e2e = подтверждённая находка без LLM.

7. e2e демо-сценарий (tools/e2e)
   - Маршрут на стенде, старт и продление сессии; журнал (admin) сверяется с эталоном по типу, зоне, порядку и времени; уведомления водителя; 403 на журнал для водителя; аудит SEC-04. Каждый шаг с тегами FR и SEC.
   - Эталон строится по реальным зонам стенда (их ~2000 вокруг Невского), строго проверяются демо-зоны. Длительность подстраивается под правила зоны.
   - Финальный прогон через запускатель CI (artifacts/07_tests/e2e/route_e2e.py): прошли 14 из 16 шагов. Работают: координаты, старт и продление сессии, ZoneExited + SessionClosed(ZoneExit) → ZoneChanged, журнал в админке, 403 для водителя.
   - Оба провала — находки backend: в событиях сессии нет пользователя (SEC-04), не создаётся session_paid.

Результаты всех проверок: JUnit XML с тегами FR/SEC (для матрицы трассируемости участника 2) + SARIF/security.json.
Тестов на мой код: 36 (агент 10, security 7, контракт 1, e2e 5, шлюз 9, генератор скриншотов 4) — все зелёные.

===== НАХОДКИ ПО СТЕНДУ (переданы участнику 3) =====
- Нет лимита частоты на POST /auth/tokens: 150 неверных паролей подряд, ни одного 429 (SEC-01, SEC-06).
- active-session для несуществующей машины отвечает 204, а не 404. Нет проверки существования и владельца; для проверки IDOR нужна вторая машина в сиде.
- В событии SessionClosed нет пользователя, аудит неполный (SEC-04).
- Регистр полей в payload событий разный (Reason/SessionId и sessionId).
- Уведомление session_paid не создаётся.
- Таймеры сессии на стенде не ускорены: предупреждение «за 10 мин» в быстром e2e не проверить.
- В сгенерированном Kotlin-клиенте по умолчанию логирование Level.BODY (токены попадают в logcat). В нашем приложении это не активно.
